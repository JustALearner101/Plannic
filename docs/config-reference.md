# ⚙️ Plannic Configuration Reference (`.plannic/config.md`)

> **The Single Source of Truth for Workspace Architecture & AI Agent Guardrails**

The `.plannic/config.md` file serves as the declarative configuration engine for Plannic. It combines structured **YAML frontmatter** (parsed and strictly validated by `@plannic/core` Zod schemas) with **Markdown body content** that AI coding agents ingest when calling the `get_config` MCP tool.

Unlike passive config files, Plannic's configuration is an **active workflow enforcement contract**: it dictates what documents are generated, how task states transition, whether audit logs are recorded, and whether AI coding agents are permitted to modify code without prior human approval.

---

## File Location & Resolution

- **Default Location**: `.plannic/config.md` in the project root.
- **Resolution**: Resolved automatically by `@plannic/fs` via `getConfigPath(cwd)`.
- **Initialization**: Automatically created via `plannic init` with sensible defaults inferred from the workspace.

---

## Configuration Schema

```yaml
---
project: <string>
stack: <string[] | string>
default_mode: "quick" | "deep"
lang: <string>
generated_docs:
  - type: "plan" | "scope" | "feature" | "phase" | "limitation"
    filename: <string>
    title: <string>
    required: <boolean>
    description: <string>
    template: <string>
ruleset:
  strict_kanban: <boolean>
  auto_changelog: <boolean>
  max_phases_recommended: <number>
  enforce_feedback_artifact: <boolean>
  plans_dir: <string>
  phase_pattern: <string>
---

## Context
High-level domain description and background information.

## Planning Rules
Mandatory architectural guidelines and constraints.
```

## Root Frontmatter Properties

### `project`
- **Type**: `string`
- **Required**: **Yes**
- **Default**: Current directory basename (if generated by `plannic init`).
- **Description**: The human-readable name of the project or workspace. Displayed in the desktop app header, CLI statusline, and rendered inline cards.

```yaml
project: Plannic Workbench
```

---

### `stack`
- **Type**: `string[]` or comma-separated `string`
- **Required**: **Yes**
- **Default**: `[]`
- **Description**: The list of primary technologies, frameworks, runtimes, and languages used in the repository.
- **AI Agent Impact**: When an AI agent reads `stack` via `get_config`, it aligns its code suggestions, build commands, test runners, and syntax choices to this specific ecosystem (e.g. using Bun instead of npm, Svelte 5 runes instead of Svelte 4 stores).

```yaml
stack: [Tauri 2, Svelte 5, TypeScript, Bun, Rust]
```

---

### `default_mode`
- **Type**: `"quick"` | `"deep"`
- **Required**: No
- **Default**: `"deep"`
- **Description**: Governs the document structure when a new plan is initialized with `init_plan`.

| Mode | Structure | Ideal Use Case |
| :--- | :--- | :--- |
| `"quick"` | A single consolidated Markdown file under `.docs/plans/<slug>.md`. | Fast prototypes, single-turn scripts, urgent bugfixes, or 1-day tasks. |
| `"deep"` | A modular document directory tree under `.docs/plans/<slug>/` containing `plan.md`, `scope.md`, `feature.md`, `phase-*.md`, and `limitation.md`. | Multi-phase initiatives, architectural refactors, core engine features, and team-facing releases. |

```yaml
default_mode: deep
```

---

### `lang`
- **Type**: `string`
- **Required**: No
- **Default**: `"id"` (or `"en"`)
- **Description**: The primary natural language code used for generated plans, task titles, and AI agent communications.

```yaml
lang: en
```

---

### `generated_docs`
- **Type**: `GeneratedDocConfig[]`
- **Required**: No
- **Default**: The standard 5-document blueprint:
  1. `plan.md` (Overview)
  2. `scope.md` (Boundaries)
  3. `feature.md` (Breakdown)
  4. `phase-1.md` (First Implementation Phase)
  5. `limitation.md` (Known Constraints)
- **Description**: Customizes which documents are scaffolded when initializing a `"deep"` plan.

#### Item Schema:
| Property | Type | Required | Description |
| :--- | :--- | :---: | :--- |
| `type` | `"plan"` \| `"scope"` \| `"feature"` \| `"phase"` \| `"limitation"` | **Yes** | Architectural category of the document. |
| `filename` | `string` | **Yes** | Target filename (e.g. `security.md`, `database.md`). |
| `title` | `string` | **Yes** | Display title rendered in navigation. |
| `required` | `boolean` | No | If `true` (default), the file is always created upon initialization. |
| `description` | `string` | No | Prompt instructions guiding the AI agent on what to write in this document. |
| `template` | `string` | No | Custom initial markdown body or template file path. |

```yaml
generated_docs:
  - type: plan
    filename: plan.md
    title: Executive Architecture Overview
    required: true
  - type: scope
    filename: scope.md
    title: Scope & Invariants
    required: true
  - type: feature
    filename: security.md
    title: Threat Model & Security Controls
    required: true
```

## `ruleset` Workflow Guardrails

The `ruleset` block is the core engine of Plannic's **Workflow Enforcement System**. It establishes guardrails that constrain autonomous AI agents from acting as unvetted code generators.

```yaml
ruleset:
  strict_kanban: true
  auto_changelog: true
  max_phases_recommended: 5
  enforce_feedback_artifact: true
  plans_dir: ".docs/plans"
  phase_pattern: "phase-{n}.md"
```

### 1. `strict_kanban`
- **Type**: `boolean`
- **Default**: `true`
- **Behavior**:
  - Tasks must strictly follow the state sequence: `todo` → `in_progress` → `done`.
  - An AI agent cannot mark tasks in Phase 2 as `done` until all acceptance criteria in Phase 1 are satisfied.
  - Prevents chaotic out-of-order execution during multi-agent or multi-phase operations.

### 2. `auto_changelog`
- **Type**: `boolean`
- **Default**: `true`
- **Behavior**:
  - Whenever an agent calls `update_document`, `move_task`, `init_adr`, or `update_spec`, Plannic creates an append-only JSONL log and version snapshot under `.docs/.history/<slug>.jsonl`.
  - Enables full auditability and rollback if an agent hallucinates or overwrites critical architectural specifications.

### 3. `max_phases_recommended`
- **Type**: `number`
- **Default**: `5`
- **Behavior**:
  - Plannic enforces iterative, focused delivery. If an agent attempts to create a plan with more than 5 phases, Plannic emits a warning advising the engineer to split the initiative into smaller, self-contained plans.

### 4. `enforce_feedback_artifact` (🔥 Core Differentiator)
- **Type**: `boolean`
- **Default**: `true`
- **Behavior**:
  - **The Golden Safety Guardrail**: AI coding agents are strictly prohibited from writing or refactoring production code without first generating a structured architectural proposal or verification plan and obtaining explicit user confirmation.
  - In Antigravity / Claude Code / Cursor, this ensures that the human software engineer remains the final decision-maker before destructive migrations, package installs, or code alterations occur.
  - Prevents the dreaded "agent run amok" problem common in unconstrained autonomous coding tools.

### 5. `plans_dir`
- **Type**: `string`
- **Default**: `".docs/plans"`
- **Behavior**: Relative path from workspace root where plan directories and files are stored.

### 6. `phase_pattern`
- **Type**: `string`
- **Default**: `"phase-{n}.md"`
- **Behavior**: Naming format for phase documents. `{n}` is replaced by the sequential phase number (e.g. `phase-1.md`, `phase-2.md`).

## Markdown Body Sections

The content below the closing `---` YAML delimiter provides freeform, context-rich guidance that is directly loaded into the AI agent's system prompt context when executing `get_config`.

### `## Context`
High-level domain knowledge, business logic constraints, target user personas, and architectural patterns.
*Example:*
```markdown
## Context
Plannic is a local-first engineering workbench for solo developers and AI agents.
It uses SQLite-free local Markdown files in `.docs/` as its sole storage mechanism.
Zero cloud dependencies.
```

### `## Planning Rules`
Non-negotiable coding and architectural principles that the AI agent must obey across every generated file and code diff.
*Example:*
```markdown
## Planning Rules
- Monochrome aesthetic: strict `#0F1117` background, 1px solid borders, zero bright gradients.
- High modularity: code belongs in `packages/*` or `apps/*`, never scattered in root.
- All writes to `.agent_activity.json` must be atomic (write to temp file then rename).
```

## Complete Examples

### Example 1: Minimalist Solo Developer (Tauri + Svelte)
```markdown
---
project: MyDesktopApp
stack: [Tauri 2, Svelte 5, Bun]
default_mode: deep
lang: en
ruleset:
  strict_kanban: true
  auto_changelog: true
  enforce_feedback_artifact: true
---

## Context
Personal productivity app built for speed and offline-first usage.

## Planning Rules
- Keep dependencies minimal; prefer web platform APIs.
- Svelte 5 runes (`$state`, `$derived`) must be used exclusively.
```

### Example 2: Enterprise Monorepo with Custom Compliance Documents
```markdown
---
project: CoreBankingService
stack: [Go, PostgreSQL, Kafka, Kubernetes]
default_mode: deep
lang: en
generated_docs:
  - type: plan
    filename: plan.md
    title: Architecture Overview
    required: true
  - type: scope
    filename: scope.md
    title: Security Boundaries & Scope
    required: true
  - type: feature
    filename: compliance.md
    title: PCI-DSS Compliance Checklist
    required: true
  - type: phase
    filename: phase-1.md
    title: Core Implementation Phase
    required: true
ruleset:
  strict_kanban: true
  auto_changelog: true
  max_phases_recommended: 3
  enforce_feedback_artifact: true
  plans_dir: ".docs/plans"
---

## Context
Mission-critical payments processor handling sensitive transaction records.

## Planning Rules
- Zero external network requests during unit tests.
- Every API route must include structured audit logging.
- Any schema migration must be accompanied by an accepted ADR in `.docs/adrs/`.
```
